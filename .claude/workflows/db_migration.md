# Database Migration Workflow

**Purpose:** Standardize the process of modifying database schemas safely, preventing data loss and ensuring local/production environments stay aligned.

**Trigger:** Use this workflow when adding new columns, tables, or altering data relationships in the backend.

## Workflow Steps

1. **Update ORM Models:**
   - Modify the database models in the backend codebase (e.g., SQLAlchemy or equivalent models).
   - Ensure constraints (nullable, unique, foreign keys) are accurately represented.

2. **Generate Migration Script:**
   - Generate the database migration file using the project's migration tool (e.g., Alembic).
   - Review the generated script to ensure it correctly captures the intended schema changes.
   - Do NOT edit the autogenerated script unless necessary for complex data migrations.

3. **Apply Migration Locally:**
   - Run the migration tool to upgrade the local database (`database_logic.db` or similar).

4. **Update Type Definitions:**
   - If the schema change affects API responses, trigger the `/sync_api_types` workflow immediately.

5. **Verify Data Integrity:**
   - Write a temporary script or run a query to verify that the core database operations (CRUD) still function as expected with the new schema.
   - For complex changes, write a test case to explicitly validate the migration logic.
